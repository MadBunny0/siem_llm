# Сценарии E2E для человека-оператора (stage-23, Глава 4 ВКР)

Три сценария проверки стенда «атака → детекция → LLM → DVE → реальная реакция
на ВМ → физический эффект». Оператор выполняет действия руками — всё пошагово.
Симуляций в системе нет: каждая реакция реально меняет состояние ВМ.

Стенд и установка агентов — [E2E_STAND.md](E2E_STAND.md); если ВМ ещё не созданы —
начни с [E2E_VM_SETUP.md](E2E_VM_SETUP.md) (VirtualBox + урезанные консольные ВМ
Kali с нуля, снимки для быстрого отката).

---

## Общие предусловия

1. Стенд по E2E_STAND поднят: `agent_control -l` — оба агента **Active**;
   `setup.sh` выполнен; AR-скрипты лежат на ВМ (`/var/ossec/active-response/bin/`).
2. Вход в UI http://localhost:3000 под `soc_lead / soclead123`
   (админ — подтверждает реакции на критичных активах, §3.4 ВКР p:102).
3. `<IP_ВМ-1>` — текущий IP ВМ-1 (`ip a` на ВМ-1), `<IP_ВМ-2>` — ВМ-2.
4. После каждого сценария: кнопка **«Сбросить реакции»** в карточке инцидента
   (выполняет обратные AR-команды) → проверить восстановление → закрыть инцидент.

## Сценарий 1 — «Подбор пароля по SSH» (реакция: block_ip)

**Шаги оператора**

1. С ВМ-2 выполнить **3–4 неудачных входа подряд** (интервал < 5 мин):
   ```bash
   ssh admin@<IP_ВМ-1>        # неверный пароль каждый раз
   ```
   Альтернатива (если установлен hydra: `sudo apt install -y hydra`):
   ```bash
   hydra -l admin -P /usr/share/wordlists/fasttrack.txt <IP_ВМ-1> ssh -t 4 -V
   ```
2. UI: в «Событиях» карточки — записи `authentication_failed` от агента
   `mail-prod-01`; создан инцидент **brute_force_attempts** (3 события за 5 мин,
   T1110). Сверить блок «Оценка критичности» (stage-22): база high за
   credential_access + повышение за критичный актив → **critical**; источник — IP ВМ-2.
3. Нажать **«✦ Запустить интеллектуальный анализ»** (~1.5–2 мин на CPU) →
   вердикт LLM, рекомендация `block_ip`, DVE: «РАЗРЕШЕНО» (оператор — админ).
4. В блоке **«Все действия playbook»** нажать **«▶ Блокировать IP»** →
   подтверждение → тост «Команда отправлена на ВМ через Wazuh active response…».
   Кнопка сменилась на «✓ Выполнено» (отметка серверная).
5. Вкладка **«Реакции (ВМ)»**: карточка `mail-prod-01` → «Блокировка IP: <IP_ВМ-2>»,
   кем/когда.

**Физическая проверка (реальный эффект)**

```bash
# с ВМ-2 — соединение не проходит:
ssh admin@<IP_ВМ-1>            # timeout / refused
ping -c 2 <IP_ВМ-1>            # нет ответа
# на ВМ-1 — правило блокировки и лог реакции:
sudo iptables -L INPUT -n --line-numbers    # DROP для <IP_ВМ-2>
tail /var/ossec/logs/active-responses.log   # запись block-ip.sh
```

**Undo**

6. В карточке инцидента **«Сбросить реакции»** → обратная команда `block-ip delete`.
   Проверить с ВМ-2: `ssh admin@<IP_ВМ-1>` — доступ восстановлен. Закрыть инцидент.

## Сценарий 2 — «SQL-инъекция на веб-сервис» (реакция: block_ip)

**Шаги оператора**

1. С ВМ-2 два запроса (ответ 404 — норм: логируется сам запрос):
   ```bash
   curl "http://<IP_ВМ-1>/index.php?id=1'%20OR%20'1'='1"
   curl "http://<IP_ВМ-1>/index.php?id=1%20UNION%20SELECT%20username,password%20FROM%20users"
   ```
2. UI: инцидент **web_attack** (2 события `web_attack` за 5 мин, T1190);
   в «Оценке критичности»: база medium за initial_access + повышение за критичный
   актив → **high**.
3. Анализ LLM → рекомендация. Реакция **«▶ Блокировать IP»** (реально,
   как в сценарии 1). Вкладка «Реакции (ВМ)» — блокировка IP ВМ-2.

**Физическая проверка**

```bash
# с ВМ-2:
curl -m 3 http://<IP_ВМ-1>/          # недоступен (timeout)
# браузер ВМ-2: http://<IP_ВМ-1>/ — тоже недоступен
# на ВМ-1: sudo iptables -L INPUT -n  — DROP для <IP_ВМ-2>
```

**Undo**: «Сбросить реакции» → `curl` с ВМ-2 снова отвечает (403/404/страница —
что угодно, кроме timeout). Закрыть инцидент.

## Сценарий 3 — «Инсайдер: бэкдор-аккаунт на сервере» (реакция: disable_account)

**Шаги оператора**

1. Легенда: злоумышленник получил сессию на критичном сервере ВМ-1. На **ВМ-1**:
   ```bash
   sudo useradd -m -s /bin/bash svc_helper
   sudo usermod -aG sudo svc_helper
   sudo passwd svc_helper
   ```
2. UI: инцидент **privilege_escalation_attempt** (1 событие `privilege_escalation`,
   T1068; severity critical: база high + критичный актив). Пользователь события —
   `svc_helper` (кастомный декодер `stand-useradd` извлекает имя учётной записи).
   Пометка: `disable_account` разрешён политикой DVE только для critical —
   на high-инциденте можно отдельно показать отказ валидации.
3. Анализ LLM → рекомендация `disable_account`. Реакция **«▶ Отключить учётную запись»**
   (цель `svc_helper` берётся из событий инцидента).
4. Вкладка «Реакции (ВМ)»: «Блокировка учётной записи: svc_helper».

**Физическая проверка (на ВМ-1)**

```bash
su svc_helper                       # authentication failure
sudo passwd -S svc_helper           # статус L (locked)
# вход по ssh под svc_helper тоже закрыт:
ssh svc_helper@localhost            # отказ
tail /var/ossec/logs/active-responses.log   # запись lock-account.sh
```

**Undo**

5. «Сбросить реакции» → обратная команда `lock-account unlock`:
   `passwd -S svc_helper` = `P`, `su svc_helper` работает. Закрыть инцидент.
