# Реальное исполнение playbook на ВМ наблюдаемых пользователей (stage-20)

До stage-20 реагирование (§3.4 ВКР) было **симуляцией**: playbook показывал, что
БЫЛО бы выполнено, но инфраструктура не менялась (осознанное отклонение 🤝 из
DEVIATIONS.md). По запросу пользователя добавлено **реальное исполнение**:
ответные действия применяются к виртуальным машинам, которые эмулируют
наблюдаемых пользователей прод-инфраструктуры. Симуляция сохранена как
отдельный режим — ДВЕ кнопки-режима, DVE один и тот же.

---

## 1. Архитектура

```
Оператор (UI, карточка инцидента)
   │  «▶ Блокировать IP» · режим: [Симуляция | Реально на ВМ]
   ▼
POST /api/v1/incidents/{id}/execute-action  {action, mode:"real"}
   │  DVE (§3.4): политика уровня риска → playbook → критический актив
   ▼
services/execution.py (диспетчер реального исполнения)
   │  инцидент → актив (Incident.asset) → ExecutionTarget (реестр, БД)
   ▼
HTTP POST {target.base_url}/agent/action  (Bearer EXECUTION_TOKEN)
   ▼
Агент на ВМ (agent/ — standalone FastAPI)
   │  меняет состояние узла: фаервол / учётные записи / изоляция / файлы
   │  журнал действий + человекочитаемый результат
   ▼
Результат → ResponseAction (БД) + аудит real_action_executed/failed + UI
```

Компоненты:

| Компонент | Где | Назначение |
|---|---|---|
| **Агент ВМ** | `agent/` (standalone, только stdlib + fastapi/uvicorn) | Эмулирует узел наблюдаемого пользователя: учётные записи, процессы, файлы, фаервол, сетевая изоляция; исполняет действия playbook; генерирует активность (алерты Wazuh → SIEM); журнал — всё видно оператору |
| **Реестр целей** | модель `ExecutionTarget` (БД), seed из env `EXECUTION_TARGETS` | Связь «актив ↔ агент»: имя цели = имя актива (Asset.name) |
| **Диспетчер** | `app/services/execution.py` | Выбор цели по активу, вызов агента, heartbeat, ResponseAction + аудит; graceful-деградация (нет цели/агент недоступен — оператор видит причину) |
| **API целей** | `app/api/execution_routes.py` | Список/heartbeat/журнал/активность/сброс/симуляция — прокси к агентам (токены не покидают бэкенд) |
| **UI** | вкладка «Агенты (ВМ)» + переключатель режима в карточке инцидента | Демонстрация: статусы агентов, журналы, проигрывание активности, режим исполнения |

## 2. Состав стенда (docker compose)

Три агента-«ВМ» (имена = seed-активы; bind-порты для наглядности):

| Сервис | Узел (hostname) | Порт | Актив в SIEM |
|---|---|---|---|
| `agent-wks` | `wks-finance-12` | http://localhost:8101/agent/status | АРМ финансиста (medium) |
| `agent-app` | `app-web-01` | http://localhost:8102/agent/status | Веб-сервер (high) |
| `agent-mail` | `mail-prod-01` | http://localhost:8103/agent/status | Почтовый сервер (critical) |

`db-primary-01` и `fw-edge-01` **целей не имеют** — инциденты на них в режиме
real возвращают `no_target` (осмысленная демонстрация: не для каждого актива
есть агент; действие доступно в симуляции).

Состояние агентов персистентно (volumes `agent_*_data`) — демонстрация
переживает перезапуск стенда; кнопка «Сбросить ВМ» возвращает узел к исходному
состоянию.

## 3. Сценарии демонстрации (каждый playbook)

| # | Playbook-действие | Как продемонстрировать | Что видно |
|---|---|---|---|
| 1 | `block_ip` | Вкладка «Агенты» → wks-finance-12 → сценарий «Подбор пароля» (4 события) → инцидент → в карточке режим «Реально на ВМ» → «▶ Блокировать IP» | В `GET /agent/status` появилось правило фаервола с IP атакующего `203.0.113.66`; журнал: «IP-адрес 203.0.113.66 заблокирован»; инцидент — отметка «Выполнено» |
| 2 | `disable_account` | Сценарий «Повышение привилегий» (bob → sudo) → действие «Блокировать учётку» | Учётная запись `bob` в статусе `locked` на агенте |
| 3 | `isolate_host` | Сценарий «Вредоносное ПО» → действие «Изолировать узел» | `isolated: true` на агенте; «Сбросить ВМ» возвращает узел |
| 4 | `collect_evidence` | Любой инцидент с активом, имеющим агента → действие «Собрать доказательства» | Снимок событий инцидента + состояние ВМ в `ResponseAction.metadata_json` (Adminer) |
| 5 | `monitor` | Любой инцидент → действие «Наблюдать» | Пассивное действие: аудит + пометка; состояние ВМ не меняется |

Пройденные DVE проверки одинаковы для обоих режимов: политика уровня риска,
наличие playbook, подтверждение администратора на критическом активе (аналитик
получит `pending_confirmation` — подтверждает soc_lead).

## 4. Поток «ВМ → Wazuh-алерт → инцидент» (наблюдаемые пользователи)

Агент умеет **проигрывать активность** (кнопка в UI или `POST /agent/simulate`):

- `normal_activity` — фоновая жизнь пользователей (входы, почта, файлы,
  внутренние IP): алерты level 3, ни одно seed-правило не срабатывает —
  демонстрация «шума», который не становится инцидентами;
- атаки (подобраны под seed-правила корреляции): `brute_force` (T1110),
  `password_spraying` (T1110.003), `repeated_scan` (T1046), `web_attack` (T1190),
  `malware` (T1204), `privilege_escalation` (T1068), `data_exfiltration` (T1048).

Каждая активность превращается в алерт формата Wazuh-менеджера
(`rule{id,level,groups}`, `agent`, `data{srcip,dstuser}`) и POST-ится в
`{SIEM_URL}/ingest/wazuh` — **тот же эндпоинт, что и настоящая интеграция
Wazuh** (integrator.sh, см. WAZUH_INTEGRATION.md). Ответ SIEM (созданные
инциденты) показывается оператору.

**Изоляция демонстрации:** у каждой ВМ свой IP атакующего (производится от
имени узла: wks-finance-12 → `203.0.113.74`, app-web-01 и mail-prod-01 — свои)
и свои локальные учётные записи (АРМ — alice/bob, веб-сервер — svc_web,
почтовый — svc_mail). Без этого корреляция SIEM (совпадение по IP/учётке/активу)
склеивала бы атаки на разные узлы в один инцидент — каждая цель демонстрируется
независимо. Явный `ATTACKER_IP` на агенте переопределяет вычисленный адрес.

## 5. Adapter: state vs linux

| Режим | Где | Что делает действие |
|---|---|---|
| `state` (стенд, по умолчанию) | контейнеры | Меняет логическое состояние узла (списки фаервола, статусы учёток, флаг изоляции) — полное изменение видно в статусе/журнале агента |
| `linux` (реальная ВМ) | Ubuntu VM | Дополнительно исполняет системные команды (`iptables`, `usermod -L`, `kill`, `mv` в карантин); требует root; недоступная команда — честная пометка в результате, логическое состояние меняется в любом случае |

Запуск агента на реальной ВМ (VirtualBox/VMware — топология из
WAZUH_INTEGRATION.md «Способ 2»): скопировать `agent/`, `pip install -r
requirements.txt`, запустить с `AGENT_HOSTNAME=<имя актива>`,
`AGENT_ADAPTER=linux`, `SIEM_URL=http://<хост>:8000/api/v1`; зарегистрировать
цель: `EXECUTION_TARGETS="<актив>=http://<ВМ>:8100|<токен>"`. Инструкция —
agent/README.md.

## 6. API (кратко)

| Метод/путь | Что |
|---|---|
| `GET /api/v1/execution-targets` | Реестр целей со статусами (JWT) |
| `POST /api/v1/execution-targets/{id}/check` | Heartbeat агента (online/offline) |
| `GET /api/v1/execution-targets/{id}/journal` | Журнал действий SIEM на ВМ (прокси) |
| `GET /api/v1/execution-targets/{id}/activity` | Журнал активности узла (прокси) |
| `POST /api/v1/execution-targets/{id}/reset` | Сброс состояния эмулируемой ВМ |
| `POST /api/v1/execution-targets/{id}/simulate` | Проиграть активность (алерты → SIEM) |
| `POST /api/v1/incidents/{id}/execute-action` | `{action, mode: "simulation"\|"real"}` |

Агент ( bearer = `AGENT_TOKEN`): `GET /agent/status` (открыт для демонстрации),
`GET /agent/journal`, `GET /agent/activity`, `POST /agent/action`,
`POST /agent/reset`, `POST /agent/simulate`, `GET /agent/health`.

## 7. Ограничения и нереализованное (важно)

| Что | Статус | Почему / что вместо |
|---|---|---|
| Реальные системные вызовы в Docker-стенде | ⚙️ эмуляция (`state`) | Контейнеры без NET_ADMIN/root: iptables/usermod недоступны — состояние узла меняется логически, изменение полностью видно в статусе/журнале агента. Реальные команды — на ВМ с `AGENT_ADAPTER=linux` |
| Windows-ВМ (netsh, LSA,Defender) | ❌ не реализован | Windows-адаптер агента не писался (стенд Linux/контейнеры); на Windows-ВМ агент запустится, но действия ограничены эмуляцией состояния. Документировано в agent/README.md |
| Автоматическая постановка Wazuh-агента на ВМ | ❌ за рамками | Установка wazuh-agent — ручная (WAZUH_INTEGRATION.md); симуляция активности агента закрывает демо-поток алертов без полной установки |
| Управление гипервизором (VirtualBox/VBoxManage: снапшоты, клонирование ВМ) | ❌ за рамками | Стенд Docker-only; ВМ создаются вручную по топологии WAZUH_INTEGRATION.md «Способ 2» |
| Реальные API фаервола периметра / EDR / IdM | ❌ заглушки | В эталоне их нет; точка интеграции — адаптеры агента/диспетчера (одна функция на интеграцию) |
| ITSM (ServiceNow/Jira) | 🤝 остаётся заглушкой | Осознанное отклонение из DEVIATIONS.md (stage-11), stage-20 его не меняет |
| Атаки в симуляторе — синтетические алерты | 🤝 демонстрационные | Генератор повторяет формат Wazuh и правила (уровни/группы), но не сетевой трафик; на стенде с настоящим wazuh-manager трафик даёт те же алерты (демо-матрица WAZUH_INTEGRATION.md) |
