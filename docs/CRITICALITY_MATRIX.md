# Матрица критичности правил корреляции и автозакрытие инцидентов

**Обновлён: 2026-11-04, stage-17**
**Источник процедуры:** [DRAFT] «Процедура определения критичности рулов в SOC», v3.1,
N. Mironov, 22.04.2026 (внутренний документ SOC, приложен пользователем).

Процедура определяет две вещи: (1) базовую критичность правила корреляции по тактике
MITRE ATT&CK; (2) правила повышения на один уровень по инфраструктурным условиям.
Этот документ описывает, как процедура реализована в прототипе и где какие веса применяются.

---

## 1. Место матрицы в конвейере

При корреляции (этап §3.3.3) severity инцидента теперь определяется так:

- у сработавшего правила корреляции **задана тактика MITRE** → критичность берётся
  из матрицы (базовая критичность тактики, максимум одно повышение — раздел 3);
- тактика **не задана** → прежняя числовая модель риска (`score` → пороги 85/65/40 — раздел 4).

При этом:

- числовой `risk_score` (0–100) считается **всегда** и остаётся метрикой для сортировки
  и отображения («Уровень риска N/100» в UI);
- критичность (`low`/`medium`/`high`/`critical`) — официальная категоризация по процедуре.

В аудите (событие `risk_calculated`) фиксируются: `severity_basis` (`mitre_matrix` |
`risk_score`), `mitre_tactic` и список сработавших причин повышения (`escalation_reasons`).

## 2. Матрица «тактика MITRE → базовая критичность»

Полная таблица из процедуры (14 тактик):

| Тактика MITRE (Tactic) | Код в системе | Базовая критичность | Комментарий (из процедуры) |
|---|---|---|---|
| Exfiltration | `exfiltration` | Critical | Вывод данных — инцидент с последствиями |
| Impact | `impact` | Critical | Нарушение работы, шифрование, уничтожение |
| Command and Control (C2) | `command_and_control` | Critical | Связь с внешним сервером — ключевой индикатор |
| Privilege Escalation | `privilege_escalation` | High | Особенно если привилегии = domain admin |
| Credential Access | `credential_access` | High | Dump паролей, токенов |
| Execution | `execution` | High | Запуск вредоносного кода |
| Persistence | `persistence` | High | Создание учётки, автозапуск |
| Defense Evasion | `defense_evasion` | High | Удаление логов, обход антивирусов |
| Lateral Movement | `lateral_movement` | High | Перемещения по сети, часто предвестник атак |
| Collection | `collection` | High | Сбор данных — этап перед эксфильтрацией |
| Initial Access | `initial_access` | Medium | Фишинг, эксплойты — потенциальный вход |
| Discovery | `discovery` | Medium | Распознавание среды — требует внимания |
| Reconnaissance | `reconnaissance` | Low | Скан, сбор инфы — ещё без доступа |
| Resource Development | `resource_development` | Low | Регистрация доменов, создание инструментов |

Seed-правила корреляции и их тактики:

| Правило | Тактика (код) | Техника MITRE |
|---|---|---|
| `brute_force_attempts` | `credential_access` | T1110 |
| `password_spraying` | `credential_access` | T1110.003 |
| `privilege_escalation_attempt` | `privilege_escalation` | T1068 |
| `web_attack` | `initial_access` | T1190 |
| `malware_detection` | `execution` | T1204 |
| `data_exfiltration` | `exfiltration` | T1048 |
| `repeated_scan` | тактика **не задана** | — |

`repeated_scan` сознательно оставлен без тактики: это универсальное правило-«шумосборка»,
срабатывающее на любой повторяющийся трафик, включая легитимный, — привязка к тактике
дала бы ложную критичность. Критичность таких инцидентов определяется числовой моделью
(раздел 4).

## 3. Правила повышения (+1 уровень)

Если правило удовлетворяет **хотя бы одному** из условий — критичность повышается на
**один** уровень: Low→Medium→High→Critical. Суммарно максимум **+1**, даже если выполнено
несколько условий; выше Critical не поднимается.

| # | Категория | Условие из процедуры | Реализация в прототипе |
|---|---|---|---|
| 1 | Критичные бизнес-активы | prod-серверы, критичные бизнес-сервисы, системы основного дохода, финансовые системы, ключевая инфраструктура | **АВТОМАТИЗИРОВАНО**: критичность актива инвентаря (`Asset.criticality`) == `critical`. Код причины: `critical_asset` |
| 2 | Персональные и конфиденциальные данные | обработка/хранение ПДн, конфиденциальная информация, закрытые репозитории, чувствительные документы/БД (не применяется при косвенном влиянии на ПДн) | **АВТОМАТИЗИРОВАНО** по маркерам (lowercase substring): `pii`, `personal_data`, `personal`, `confidential`, `gdpr`. Код: `personal_data` |
| 3 | Атаки с внешнего периметра | брутфорс VPN, атаки на внешние веб-ресурсы, подбор к интернет-экспонированным сервисам, «долбёжка» периметра | **АВТОМАТИЗИРОВАНО** двумя способами: (а) маркеры `vpn`, `perimeter`, `internet_facing`, `external_attack`; (б) событие с непустым `src_ip` на активе сегмента DMZ/edge/internet, при этом `src_ip` не входит во внутренние сети (RFC1918: 10/8, 172.16/12, 192.168/16 + loopback + link-local — ручной список; сознательно без `ipaddress.is_private` из-за различий версий Python). Код: `perimeter` |
| 4 | Административные панели и зоны управления | админ-панели, консоли управления, cloud control plane, гипервизоры, системы централизованного управления (не применяется, если просто нужен root-доступ для совершения действия — этот нюанс проверяется человеком при брейншторминге правила) | **АВТОМАТИЗИРОВАНО** по маркерам: `admin_panel`, `admin_console`, `management`, `cloud_control`, `hypervisor`, `vcenter`, `control_plane`. Код: `admin_zones`. Голые слова `admin`/`web`/`ll` сознательно **не** используются как маркеры — ложные срабатывания |
| 5 | События из LL | правило пришло после LL, pentest, red team и аналогичные (исключение — [BB] события) | **АВТОМАТИЗИРОВАНО частично**: маркеры `pentest`, `red_team`, `redteam`, `purple_team`. Код: `ll_redteam`. Различение LL/[BB] — за человеком: маркер ставится в группы при заведении правила |
| 6 | Аварийные механизмы / «стоп-кран» | debug-механизмы, аварийные команды, инструменты вне штатной эксплуатации, ручные обходные механизмы | **АВТОМАТИЗИРОВАНО** по маркерам: `debug`, `emergency`, `kill_switch`, `bypass`, `manual_override`. Код: `stop_crane` |
| 7 | Отдельно отмеченные критичные события поставщика логов | на этапе брейншторминга поставщик логов/СЗИ указал событие как крайне значимое (применяется даже вне других категорий) | **РУЧНОЙ ФЛАГ**: чекбокс `escalated_by_vendor` в карточке правила корреляции (CRUD UI, поле БД `correlation_rules.escalated_by_vendor`). Код: `vendor_flag` |

Где ищутся маркеры: группы Wazuh (`rule.groups`) **всех связанных событий**, `event_type`,
имя и описание правила корреляции — без учёта регистра, по подстроке.

## 4. Веса числовой модели риска (score) и их обоснование

Источник соображений: §3.3.3 ВКР (p:69–80) требует интегральную оценку риска из **пяти**
факторов; конкретные числовые значения — калибровка прототипа, выбранная из следующих
соображений. Формула:

```
score = min(100, max(оценок по событиям) + бонус_серии × p_implement × достоверность)
```

| Фактор | Значение/вес | Обоснование |
|---|---|---|
| Критичность актива (добавляется к кандидату оценки) | critical→100, high→75, medium→60, low/нет→нет вклада | Критический актив сам по себе означает максимальный потенциальный ущерб (порог critical 85 достигается активом без дополнительных факторов — «атака на критичный актив априори серьёзна»); high=75 — между порогами high (65) и critical (85): нужен хотя бы слабый дополнительный фактор, чтобы стать critical; medium=60 — выше порога high 65 не хватает (medium-актив сам не даёт high), но перекрывает medium (40) |
| Уровень правила Wazuh | `LEVEL_TO_SCORE = min(100, level×7)`: уровень 15 → 100, уровень 3 → 21 | Линейная шкала «сырой опасности» события источника; множитель 7 подобран так, чтобы верхний уровень шкалы Wazuh (15) точно достигал 100 |
| Опасность типа атаки (`ATTACK_TYPE_DANGER`, максимум совпадений по event_type/группам) | privilege 95, exfiltration 95, malware 90, credential 85, brute 80, authentication_failed 60, scan 55 | Веса согласованы с матрицей тактик: техники с наибольшим ущербом/ключевыми индикаторами (повышение привилегий, кража данных) стоят в диапазоне critical (≥85); запуски ВПО и компрометация учётных данных — в диапазоне high (65–84); перебор паролей — верхняя граница high (80); неудачные попытки входа и сканирование — middle/low диапазон (55–60), т.к. это ещё не доступ |
| Бонус за серию событий | +5 за каждое связанное событие сверх первого, максимум +20 (5 событий) | Серия подтверждает систематичность атаки, но не должна сама по себе превращать одиночную низкую активность в critical; потолок 20 = половина интервала между порогами medium/high |
| Вероятность реализации (p_implement) | из данных — явный `rule.confidence` алерта или `level/15`, зажат в [0.05, 0.95] | Правило уровня 15 почти наверняка реализуется (0.95), уровня 3 — минимально (0.2); зажим исключает вырожденные 0 и 1 |
| Достоверность корреляции (correlation_confidence) | средняя доля совпавших признаков (IP/учётка/актив) между связанными событиями, 1/3…1.0; одиночное событие = 1.0 | Чем больше признаков связывает события, тем выше уверенность, что это одна атака, а не шум; бонус серии умножается на неё — сомнительная корреляция не накручивает оценку |
| Пороги `score_to_severity` | ≥85 critical, ≥65 high, ≥40 medium, иначе low | 85 — critical начинается с «почти максимум» шкалы (критичный актив 100, privilege 95, malware+что-либо); 65 — high заметно отделён от medium; 40 — граница «уже заметно, но ещё не срочно» |

Важно: с stage-17 для правил **с тактикой MITRE** числовая модель влияет только на
`risk_score`, но не на severity (severity — по матрице); для правил **без тактики** —
как раньше.

## 5. Автоматическая обработка инцидентов: автоконвейер low и ручной запуск остальных

Конфигурация (`.env`, `app/config.py`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `AUTO_ANALYSIS_LEVELS` | `critical,low` | уровни, анализируемые LLM автоматически после ingest и `POST /demo/populate` (плановый режим, §3.3.3 p:80) |
| `AUTO_RESPONSE` | `false` | режим исполнения реагирования (`false` = dry run, симуляция) |
| `AUTO_CLOSE_LEVELS` | `low` | уровни **полного автоматического конвейера**: после успешного автоанализа одобренные DVE действия исполняются системой и инцидент закрывается; пусто = автоконвейер выключен для всех уровней |

Разделение режимов (stage-17, фидбек):

- **low (автоконвейер)** — весь пайплайн без человека: ingest → автоанализ LLM →
  рекомендация проходит DVE → действия исполняются системой (симуляция при
  `AUTO_RESPONSE=false`) → инцидент закрывается автоматически. При закрытии:
  аудит-событие `incident_auto_closed`, ITSM-уведомление `incident_auto_closed`,
  в `response_raw` анализа пометка `auto_closed: true`.
- **medium / high / critical (ручной режим)** — анализ может быть автоматическим
  (critical) или ручным, но playbook выполняет **оператор**: владелец инцидента
  или администратор кнопкой «▶ Выполнить» (`POST /incidents/{id}/execute-action`,
  при `AUTO_RESPONSE=false` — dry run). Результаты такого анализа приходят с
  `execution.mode = manual_run` («ОЖИДАЕТ ЗАПУСКА» в UI, в конвейере Playbook
  показан активным этапом «ожидает запуска оператором»), аудит —
  `action_awaiting_manual_run`. Заблокированное DVE действие не исполняется вовсе
  (`mode = blocked`, оператор видит причину).

Защиты автозакрытия — инцидент **не** закрывается, если:

- действие отложено до подтверждения администратора (`pending_confirmation` — например,
  критический актив + `block_ip`);
- инцидент уже закрыт;
- инцидент закреплён за аналитиком (`analyst_id` установлен) — человек уже вмешался;
- анализ завершился ошибкой LLM.

Ручной анализ никогда автоматически не закрывает инцидент — автозакрытие только
в фоновом конвейере (`run_auto_analysis`).

Проверка на стенде: «🎬 Мок-сценарии» (`POST /demo/populate`) с stage-17 тоже
запускает автоанализ для уровней из `AUTO_ANALYSIS_LEVELS` — после прогона low-инциденты
закрыты, у critical есть рекомендации, ожидающие ручного запуска (в тосте —
«автоанализ запущен: N»).

## 6. Как проверить на стенде

1. Пересобрать и поднять стенд: `docker compose up -d --build`.
2. Открыть Swagger: http://localhost:8000/docs → `GET /correlation-rules` — в правилах
   появились поля `mitre_tactic`, `mitre_technique`, `escalated_by_vendor`.
3. `PUT /correlation-rules/{id}` — выставить правилу тактику (например,
   `credential_access` для `brute_force_attempts`).
4. `POST /demo/test-event` — событие уходит в фоновый анализ; в аудите (`risk_calculated`)
   проверить `severity_basis`, `mitre_tactic`, `escalation_reasons`.
5. Для инцидента уровня `low`: после автоанализа он должен закрыться сам — статус
   `closed` в списке инцидентов, аудит-событие `incident_auto_closed`.
