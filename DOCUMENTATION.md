# СИСТЕМА УМНОЙ ОБРАБОТКИ ИНЦИДЕНТОВ ИНФОРМАЦИОННОЙ БЕЗОПАСНОСТИ (SIEM + LLM)

Полноценный учебно-экспериментальный стенд интеллектуальной обработки инцидентов информационной безопасности:

**Wazuh → прием события → нормализация → корреляция → оценка риска → Qwen2.5-3B → Decision Validation Engine → Playbook → Audit Log → Web-интерфейс**

---

## ЭТАП 1. ТЕОРИЯ. Бизнес-идея и зачем это нужно

### Что такое SIEM

**SIEM** (Security Information and Event Management — система управления событиями и информацией информационной безопасности) — это централизованная платформа, которая:

1. **Собирает** логи и события безопасности со всех систем организации (серверы, сетевые устройства, фаерволы, приложения, базы данных).
2. **Нормализует** их в единый стандартный формат, чтобы можно было сравнивать разнородные события.
3. **Коррелирует** — сопоставляет события во времени и по признакам, выявляя сложные атаки, которые по отдельным алертам не заметны.
4. **Оценивает опасность** — назначает уровень риска инцидентам.
5. **Alertирует** Security Operations Center (SOC) о критических событиях.
6. **Ведёт аудит** — хранит полную цепочку событий для расследований и отчётности.

Проще говоря: SIEM — это «единое окно» для аналитиков безопасности, где видна вся картина угроз в организации.

### Что такое SOAR (этот проект)

Разработанный модуль — это **SOAR**-компонент (Security Orchestration, Automation and Response). Он **не заменяет SIEM**, а **расширяет** её:

- Берёт алерты от SIEM (в нашем случае **Wazuh**),
- Автоматически анализирует их с помощью локальной нейросети (LLM),
- Принимает решение о реагировании (блокировка IP, отключение учётной записи, изоляция хоста),
- Выполняет эти действия **автоматизированно по заранее согласованным правилам**,
- Ведёт подробный журнал всех решений для отчётности.

### Бизнес-цель проекта

**Проблема**, которую решает проект:

> SOC-аналитик получает **сотни алертов в день** от SIEM. 90% из них — ложные срабатывания или рутинные события (неудачные попытки входа, сканирование портов). Аналитик вручную перебирает их, тратя десятки минут на каждый инцидент, а критические угрозы могут затеряться в шуме.

**Решение**:

1. **Автоматическая нормализация** — из сырых логов Wazuh извлекаются структурированные поля (пользователь, IP, тип события, уровень опасности), всё приводится к единому формату.
2. **Корреляция по правилам** — вместо того чтобы смотреть на каждый алерт по отдельности, система объединяет события в инциденты: например, 10 неудачных попыток входа с одного IP за 5 минут превращаются в **один** инцидент «brute-force атака».
3. **Оценка риска** — каждый инцидент получает балл (0–100) и категорию (low/medium/high/critical) с учётом:
   - уровня опасности события из Wazuh,
   - **критичности защищаемого актива** (атака на критический сервер = максимальный риск),
   - бонус за серию связанных событий (корреляция).
4. **Интеллектуальный анализ через LLM** — для инцидентов высокой и критической категории подключается локальная языковая модель **Qwen2.5-3B** (запускается в **Ollama**). Модель работает **без интернета, приватно**, и выдает обоснованное решение с объяснением и степенью уверенности.
5. **Decision Validation Engine (фильтр безопасности)** — решение модели **не выполняется слепо**: система сверяет его с политикой, привязанной к уровню риска. Например, при severity `low` модель *не может* предложить `block_ip` — действие заменится на безопасный `monitor`.
6. **Playbook (автоматизированное реагирование)** — если решение одобрено, выполняется заранее подготовленный сценарий из базы (`block_ip` → команда фаерволу; `disable_account` → блокировка учётной записи). **По умолчанию режим безопасный** (`AUTO_RESPONSE=false`): playbook **симулирует** действие и записывает его в БД, но не меняет инфраструктуру.
7. **Audit Log** — каждый шаг пайплайна (приём, нормализация, корреляция, оценка риска, анализ LLM, валидация, выполнение playbook) записывается в журнал аудита с привязкой к инциденту/событию/пользователю. Это обеспечивает полную подотчётность решений.
8. **Web-интерфейс** — React-дашборд, где аналитик видит список инцидентов, их детализацию, рекомендации модели, историю аудита и может запустить анализ вручную.

### Бизнес-пример использования

**Сценарий: brute-force атака на сервер компании**

*Без проекта:*
1. Wazuh шлёт 10 отдельных алертов «неудачная попытка входа» с IP `192.0.2.10`.
2. Аналитик вручную открывает каждый алерт, сверяет время, определяет, что это одна серия.
3. Ручком идёт в фаервол, вводит `iptables` команду на блокировку — может ошибиться.
4. Никто не ведёт детального журнала, при расследовании не понятно, кто и когда принял решение.

*С проектом:*
1. Wazuh шлёт алерты → система **нормализует** их в единую структуру.
2. **Корреляция**: находит 9 похожих событий от того же IP за 5 минут → создаёт **один инцидент** из 10 событий.
3. **Оценка риска**: уровень 10 из событий + бонус за серию (+20) + критичность сервера → **риск = 90, severity = critical**.
4. **LLM** получает контекст → предлагает `recommended_action: "block_ip"` с объяснением.
5. **Decision Validation Engine**: для `critical` действие `block_ip` **разрешено политикой** → одобряет.
6. **Playbook** загружает сценарий `block_ip` → шаг «выполнить `iptables -A INPUT -s 192.0.2.10 -j DROP`».
7. **Audit Log** фиксирует: кто/что инициировал, когда, почему, какое действие выполнено.
8. Аналитик видит всё в **веб-интерфейсе** и может вмешаться в любой момент.

## ЭТАП 2. ПРАКТИКА. Внутреннее устройство проекта

### 1. Инструменты и стек

| Слой | Технология | Зачем |
|---|---|---|
| **Backend API** | Python 3.12 + **FastAPI** + uvicorn | HTTP-сервер, принимает алерты, отдаёт данные фронтенду. FastAPI даёт автоматическую валидацию запросов (Pydantic) и документацию `/docs`. |
| **База данных** | **PostgreSQL 16** | Хранит события, инциденты, правила корреляции, playbooks, логи аудита, пользователей, активы. Подключение через **SQLAlchemy 2.x** + **psycopg3**. |
| **ORM** | SQLAlchemy 2 | Работа с БД: модели, запросы, сессии. |
| **LLM-движок** | **Ollama** + модель **`qwen2.5:3b`** | Локальная языковая модель для анализа инцидентов — работает без интернета, приватно, бесплатно. |
| **Frontend** | **React 19** + **Vite** | Dashboard для аналитиков: список инцидентов, фильтры, кнопка «анализировать». |
| **Развёртывание** | **Docker / Docker Compose** + Nginx | Всё поднимается одной командой `docker compose up --build`; PostgreSQL и Ollama в изолированных контейнерах, данные сохраняются в volumes. |
| **Тесты** | **pytest** | Автоматическая проверка сервисов (папка `tests/`). |
| **Исходный SIEM** | **Wazuh** | Поставщик событий (через HTTP POST) + виртуальный экспериментальный стенд на **VirtualBox**. |

### 2. Базы данных: какие таблицы за что отвечают

Все модели определены в **`app/models.py`**:

| Таблица | Назначение |
|---|---|
| **`users`** | Пользователи системы (аналитики SOC): логин, хеш пароля, роль, дата создания. |
| **`assets`** | Защищаемые активы (серверы, БД, сетевые устройства): название, описание, **критичность** (`critical`/`high`/`medium`/`low`). **Именно критичность актива влияет на итоговый риск** — атака на критический сервер даёт максимальный балл. |
| **`events`** | Нормализованные события из Wazuh: `timestamp`, `source`, `event_type`, `user`, `src_ip`, `asset_id`, `criticality_level`, `raw_message`, `raw_data` (полный исходный JSON для расследований). Связь «многие ко многим» с инцидентами. |
| **`incidents`** | Инциденты: `title`, `description`, `severity` (low/medium/high/critical), `status`, `asset_id`, `attack_type`, `risk_score`, `analyst_id`, связь с событиями/анализами/ответными действиями. |
| **`analyses`** | Результаты анализа LLM: инцидент, модель, промпт, ответ модели (рекомендация + валидация + выполнение). |
| **`correlation_rules`** | **Правила корреляции из БД** (ключевое нововведение): `name`, `conditions` (JSON: поле, оператор `eq/neq/in/like`, значение), `time_window_minutes`, `priority`, `is_active`. Раньше корреляция была жёсткой (`src_ip` + `dstuser`), теперь — **настраиваемая без изменения кода**. |
| **`playbooks`** | Сценарии автоматизированного реагирования: `name`, `description`, `trigger_conditions`, `allowed_actions`, `steps` (порядок операций, например блокировка IP через фаервол), `priority`, `is_active`. |
| **`response_actions`** | Выполненные ответные действия: привязка к инциденту, playbook, тип действия (`block_ip`, `disable_account`…), результат, кто инициировал (`playbook`/`validation`/`manual`), метаданные. |
| **`audit_logs`** | **Журнал аудита всех этапов**: `timestamp`, `event_type` (`event_ingested`, `normalized`, `correlated`, `risk_calculated`, `llm_analyzed`, `playbook_selected`, `action_executed`, `validation_result`), привязка к инциденту/событию/пользователю, детали. |

#### Пайплайн: как одно событие пробегает через систему

1. **Приём (`POST /api/v1/ingest/wazuh`)** — FastAPI получает JSON-алерт Wazuh (валидируется Pydantic-схемой `WazuhAlert`).

2. **Нормализация (`app/services/normalization.py`)** — `normalize_wazuh(alert)` извлекает из сырого JSON Wazuh стандартизированное представление: `timestamp` → datetime (парсит `Z`-суффикс, падает на `datetime.now()` при ошибке), `source` = имя агента / ID / srcip / `wazuh`, `event_type` = первая группа из `rule.groups` (`authentication_failed`), иначе `security_event`, `user`, `src_ip` из `data`, `criticality_level` = `rule.level` (0–15, мапится в баллы), `raw_message` = `full_log`, `raw_data` = исходный JSON целиком.

3. **Сохранение события в БД** → таблица `events`.

4. **Корреляция (`app/services/correlation.py`)** — загружаются **активные правила** из `correlation_rules`; `match_condition()` проверяет **одно условие**: операторы `eq` (равно), `neq` (не равно), `in` (в списке), `like` (содержит подстроку) над полями `src_ip`, `user`, `event_type`, `criticality` или произвольным полем из `raw_data`. Все условия должны выполняться (`all()`). Если правило сработало, из БД вырезаются события за `±time_window_minutes` (окно корреляции, по умолчанию 5 мин). Возвращается дедуплицированный список связанных событий + само событие.

5. **Оценка риска (`app/services/risk.py`)** — `LEVEL_TO_SCORE = {str(i): min(100, i*7) for i in range(16)}` → уровень 0→0, 3→21, 10→70, 15→100; **дополнительный балл за критичность актива** (critical→100, high→75, medium→60); `base = max(баллы)`; `bonus = min(20, max(0, len(events)-1)*5)` — +5 за каждое связанное событие сверх первого (корреляция), макс. +20; `score = min(100, base + bonus)`; `score_to_severity()`: ≥85 → `critical`, ≥65 → `high`, ≥40 → `medium`, иначе `low`. По результату создаётся/обновляется `Incident`.
